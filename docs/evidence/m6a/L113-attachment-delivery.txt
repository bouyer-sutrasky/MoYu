## 1. 红：为什么平台必须先能力协商

旧运行时对 trigger 请求体是 `.strict()`：未知键直接 **400**，而平台客户端把 400 当**不可重试失败**
（`RuntimeClient` 只在 5xx/408/429 重试，`delivery` 对不可重试错误写 `failed`）。旧平台代码里
没有任何附件字段：

$ git show d55c722^:apps/dispatcher/src/delivery.ts | grep -c attachments
0

旧 Bridge 的既有契约测试（patch 0002，未改动）：

$ git show aa9b6cd:integrations/superagent/patches/0002-machine-bridge.patch | grep -n 'nope: true'
780:+    expect(await call('POST', '/bridge/v1/triggers', { nope: true })).toMatchObject({ status: 400 })

即：若平台"先发再说"，旧运行时会把消息打成 400 且不再重试。因此本轮把"能力匹配才带附件"作为头号判据，
旧运行时只收 text（附件在 delivery evidence 里显式标未投递），见 §2.2 的两条集成测试。

## 4. 未验证 / 已知缺口

1. **图像读取没有真实证据**：当前执行器模型配置（`/root/.dsh/profiles/superagent/cordis.patch.yml`）
   没有给 `deepseek/deepseek-v4.1-flash` 声明 `inputModalities`（该文件 `inputModalities` 出现次数：
   0）。Harness 的 `read_image` 会直接拒绝：
   `model "..." does not declare image input; switch to an image-capable model to read images`。
   因此本环境无法完成"真实截图任务让模型看见像素"的验收；需要所有者按设计 §8 决策 2 指定一个
   image-capable 模型（或为该模型补模态声明），我才能补这项证据。
2. **真实 worker 会话未跑**：本轮没有起带模型的完整隔离 runtime（图像前置条件缺失），因此
   "文本按需读取"只有交付/落盘与卡片形状的证据，没有真实 `read` 工具调用的会话事件。
3. 设计 §3.1 原写"错误仓库令牌 → 404"，实现为 **401**：`verifyCallbackToken` 无法从令牌反查仓库，
   与 runtime-events 一致；设计文档已同步。
4. 运行时整套测试的 3 条 Feishu/shim 失败是环境相关的既有失败（基线与改动后相同），不是本补丁引入。
